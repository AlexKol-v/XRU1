## 2. Состояние кода

- Код укрытий не менялся с коммита `487af99` (три коммита назад).
- Всё текущее — **незакоммиченный рабочий каталог**.
- В укрытиях за сессию осталась ОДНА правка по существу:
  `MatchesActiveCoverHit` больше не сравнивает `UPrimitiveComponent`.
  Одна стена = одна плоскость (нормаль + удаление), допуск 16 см.
  **Подтверждено логом**: ложные края на 15/30/45 см исчезли.
  Причина — модульные уровни: визуально сплошная стена это десяток мешей.
- Всё остальное, что я вносил в укрытия (арочное правило фланга, флаг
  `bLegacyGeometricFlanking`, сбор сторон на лету, толстая сфера в пробе края,
  `PeekEdgeMaxDistance = 200`), **откачено как переусложнение**.

## 3. Что НЕ является багом (проверено, не трогать)

- **`PeekEdgeMaxDistance = 60` — правильное значение.** Это «насколько близко я
  к углу, чтобы считать себя стоящим у угла», ≈ ширина плеч. Двухметровый
  «угол» — бессмыслица.
- **AnimBP в порядке.** Проверено через MCP (`unreal_ue`, domain `anim`,
  `get_info` + `get_transitions`) на `/Game/XRU1Game/Units/Anim/ABP_Solider`:
  машины `SM_CrouchCover` и `SM_HighCover`, у обеих состояния `Loop` и `Look`
  и обе переходные связи (Loop→Look, Look→Loop, duration 0.15).
- **`UpdateCoverPeek` вызывается каждый тик**, ранних выходов в `AUnitBase::Tick`
  нет.
- **Прижатие к стене работает.** Свип отрабатывает, сдвиги 5–28 см; юнит с
  сдвигом 1 см просто уже стоял вплотную.

## 4. Найденный архитектурный дефект — ДВА ИСТОЧНИКА ПРАВДЫ

В `AUnitBase::RebuildVisualState` (`Source/XRU1/Tactics/UnitBase.cpp`, ~строка 199):

```cpp
// Источник A: сторона клипа Look_Left/Look_Right — из направления НА СТЕНУ
if (FMath::Abs(State.CoverDirectionLocal.Y) > 0.35f)
    State.PeekSideLocal = FMath::Sign(State.CoverDirectionLocal.Y);

// Источник B: «есть ли куда выглядывать» — из другой функции,
// а её ВЕКТОР НАПРАВЛЕНИЯ К КРАЮ выбрасывается, остаётся только bool
bHasPeekEdge = !Cover->FindPeekEdgeSide(EdgeDistance).IsNearlyZero();
```

`UCoverDetectionComponent::FindPeekEdgeSide` возвращает мировой вектор к
ближайшему краю и дистанцию до него. Это и есть «плясать от нормали стены».
Но сторону выглядывания считают из совершенно другой величины.

Плюс: `FindPeekEdgeSide` дёргается из `RebuildVisualState`, то есть на **каждый**
`NotifyUnitStateChanged` — до 8 трейсов на вызов, без кэша. В логе видно, как
одна строка печатается по 6 раз подряд.

## 5. ОТКРЫТЫЙ ВОПРОС — почему не срабатывает выглядывание

Условия в `AUnitBase::UpdateCoverPeek`:

```
Pose == CrouchCover || HighCover
&& !VisualState.bMoving
&& bHasPeekEdge
&& PeekSideLocal != 0
&& CoverIdleTime >= NextPeekDelay   (сейчас 2–5 с)
```

Край в логе находится, значит `bHasPeekEdge` истинен. Остаётся вилка из двух
непроверенных ветвей:

1. **Поза не является позой укрытия.** Например юнит в Overwatch — тогда
   `Pose == Overwatch`, и выглядывание запрещено by design.
2. **`PeekSideLocal == 0`.** Так бывает, когда `HugCover` НЕ нашёл край и
   развернул юнита спиной к стене: тогда `CoverDirectionLocal.Y ≈ 0`, порог
   `> 0.35` не проходит, сторона остаётся нулевой.

**Первый шаг новой сессии — закрыть эту вилку одной строкой лога**, а не
догадками. Добавить в `UpdateCoverPeek` под `xru1.Cover.Debug` печать причины
отказа: поза / движение / край / сторона / сколько накоплено времени.
Один прогон PIE — и причина известна точно.

## 6. Что делать после того, как причина известна

Рефакторинг «единый источник» (согласован с заказчиком):

1. `FindPeekEdgeSide` становится **единственным** источником: из него берутся
   `bHasPeekEdge`, `PeekSideLocal` (переводом мирового вектора в локальные оси)
   и доворот в `HugCover`. Формула из `CoverDirectionLocal.Y` удаляется.
2. Результат **кэшируется** в `UCoverDetectionComponent` при
   `EvaluateSurroundings`, а не пересчитывается трейсами на каждый
   `NotifyUnitStateChanged`.
3. Проверить инвариант: после `HugCover` юнит смотрит ВДОЛЬ стены на край,
   поэтому в локальных осях край впереди (X), а стена сбоку (Y). Сторона клипа
   должна выводиться из края, но с учётом этого разворота — это и есть место,
   где прежняя реализация свернула на «сторону стены».

## 7. Best practices (изучено)

Универсального алгоритма края нет, все делают сэмплирование вдоль касательной:
[в The Last of Us каждому NPC назначали 20 cover-постов и бросали ~160 лучей в
кадр](https://arxiv.org/pdf/2207.00682). Важное предостережение:
[луч, попавший в ребро коллайдера, возвращает интерполированную нормаль](https://forum.unity.com/threads/dealing-with-raycast-corner-normals.777716/)
— у самого угла нормали врут. Вывод: опираться на **плоскость активной стены**
(нормаль + удаление), а не на нормаль каждого отдельного попадания. Наш алгоритм
по сути верный; ломало его именно опознание «та ли это стена».

## 10. ИТОГ (сессия 2026-07-30, вторая): причина доказана, §6 выполнен

Диагностика: строка `[Peek]` в `AUnitBase::UpdateCoverPeek` под
`xru1.Cover.Debug` — печатает причину отказа, кэш `VisualState` рядом с живым
опросом тех же величин, сторону и накопленный таймер. Оставлена в коде.

**Вилка §5 закрыта прогоном PIE: ветвь 2, `PeekSideLocal == 0`.**

- Конвейер выглядывания сам по себе работал: Medic и Sniper копили таймер и
  циклично выглядывали. Ветвь 1 (поза Overwatch) не встретилась ни разу.
- Застревали юниты, стоящие НЕ вдоль стены (`CoverDirectionLocal.Y` =
  0.02–0.21 < порога 0.35) при живом крае (`bHasPeekEdge=1`) — Assault, Tank,
  Marauder. Сторона из фактического поворота актора = второй источник правды
  из §4, он и стрелял.

**Второй доказанный дефект (Tank):** `MakeCoverCandidate` фиксирует кандидата
с `WallId != 0`, но ПУСТЫМ `HitComponent`, если контрольный луч не подтвердил
поверхность. `MatchesActiveCoverHit` требовал `ActiveCoverComponent.IsValid()`
→ каждая проба края проваливалась → ложный край на первом шаге (в логе:
«стена есть, но НЕ active, active=None»). Требование противоречило решению §2
«одна стена = одна плоскость» и удалено.

**Сделано (рефакторинг §6, единый источник):**

1. Край и сторона считаются ОДИН раз в `EvaluateSurroundings`, атомарно с
   активной геометрией, и кэшируются в `UCoverDetectionComponent`:
   `PeekEdgeDirection`, `PeekEdgeDistance`, `PeekSideSign`, `HasPeekEdge()`.
2. `PeekSideSign` — из геометрии стены и края в ПРОЕКТНОЙ стойке (боец вдоль
   стены лицом к краю): `sign(dot(ToWall, cross(Up, EdgeDir)))`. От поворота
   актора не зависит; в правильной стойке совпадает с прежним
   `sign(CoverDirectionLocal.Y)`. Формула из `CoverDirectionLocal.Y` удалена.
3. `RebuildVisualState`, `HugCover`, `FacePeekEdge` читают кэш — трейсов на
   `NotifyUnitStateChanged` больше нет (было до 8 лучей на вызов).
4. `MatchesActiveCoverHit` больше не требует валидного `ActiveCoverComponent`
   (плоскость решает сама, см. выше).

**Открытым осталось (не блокирует выглядывание):** ПОЧЕМУ юниты после
settlement стоят носом в стену, а не вдоль неё (лог не фиксирует таймлайн
поворотов; кандидаты — `bOrientRotationToMovement` во время подшага, перевыбор
стены при финальном `EvaluateSurroundings` в `TryFinalizeMoveSettlement`).
После §6 это чисто косметика стойки: сторона и выглядывание от поворота больше
не зависят. Маркер в логе: `сторона=±1` при `CoverDirLocal.Y≈0`.

### Прогон 2 (после §6) — фикс подтверждён

- Все ранее заблокированные юниты выглядывают циклично: Marauder разблокирован
  в ТОЙ ЖЕ стойке (Y=−0.02 → сторона=+1), Assault (−0.35→−1), Tank (−0.71→+1).
- Ложный край Tank исчез: пробы чистые, `active` валиден.
- У Sniper сторона=+1 при Y=−0.24 — старая формула дала бы −1 (не тот клип).
- Единственный отказ: Medic — «край НЕ найден (0 см при лимите 60)» БЕЗ единой
  строки пробы = все пробы совпали с active-плоскостью в обе стороны. Либо
  честная глухая стена (by design), либо пробы клеят ЧУЖУЮ коллинеарную стену
  по плоскости (§2). Лог этих случаев не различал.

Логи усилены (все под `xru1.Cover.Debug`):
- сводка каждого `EvaluateSurroundings`: позиция, cover, стена
  удержана/перевыбрана, active-актор, итог по краю и стороне;
- ветка «край НЕ найден» печатает акторов последних совпавших проб по обеим
  сторонам — различает длинную стену и склейку чужой коллинеарной;
- след доворотов HugCover: плановый yaw в «прижатие» и при завершении подшага —
  расхождение итоговой стойки в [Peek] с планом = юнита развернул кто-то после.

### Прогон 3 — найдена причина «не прижимается и не доворачивается»

Сводки evaluate показали: ПОЗИЦИЯ ЮНИТА НЕ МЕНЯЕТСЯ после «прижатия» (план
45 см → факт 1 см), и строка «подшаг завершён» не печатается никогда.

**§3 этого документа ошибался: прижатие НЕ работало.** В логе печатался ПЛАН
сдвига (свип), а не факт. Причина — самоотмена: `UpdateCoverHugStep` первой
строкой проверял `IsUnitInTransit`, который засчитывает СКОРОСТЬ, а скорость
создаёт сам подшаг (плюс остаточное торможение после прибытия). Шаг убивал
себя на первом тике через `FinishCoverHugStep(bApplyCoverFacing=false)` — и
этот же флаг молча отменял отложенный доворот к краю. Один баг = оба симптома.

Починено:
1. Отмена подшага — только по НОВОМУ ПРИКАЗУ (`AUnitAIController::IsMoving`,
   path following), скорость больше не участвует.
2. Дальность подшага = `CoverTraceDistance` тюнинга (та же дистанция, что
   засчитала укрытие) вместо фиксированных 45 см: юнит, вставший «в укрытии»
   в метре от стены, теперь дошагивает до неё. `CoverHugMaxNudge` остался
   только выключателем (0 = без шага).
3. Свип, не нащупавший стену, больше не даёт слепой шаг — только доворот.

Отдельно (пользователь): агент какой-то из прошлых сессий удалил в ABP бленд
выглядывания (ноги стоят, торс выглядывает) — в Look-состоянии стоял idle.
Анимации в ABP пользователь настраивает сам; C++ их не трогает.

### Прогон 4 — самоотмена подшага, вторая итерация

Замена IsUnitInTransit на `AUnitAIController::IsMoving()` НЕ вылечила: план
21–55 см, факт 0–1 см, «подшаг завершён» не печатается. Причина — IsMoving()
включает `PendingSettlementUnit` и `IsMoveSettlementInProgress()`, то есть
**сам подшаг** (settlement взводится в BeginMoveSettlement сразу после
HugCover). Семантика IsMoving = «перемещение не завершено ЦЕЛИКОМ, включая
settlement» — для occupancy верно, как признак «новый приказ» — самоубийство.

⚠️ Урок: настоящий новый приказ во время подшага и так невозможен —
`MoveAlongRoute` возвращает Failed при живом settlement. Проверка в
`UpdateCoverHugStep` заменена на прямой `GetMoveStatus() != Idle` (страховка
от MoveTo* мимо MoveAlongRoute) с логом отмены.

Логи по запросу пользователя: [Peek]-диагностика УДАЛЕНА (шумела, своё
доказала); подшаг покрыт полностью: старт (см и цель), навмеш-урезание цели,
«не нужен (< допуска)», отмена по приказу, дошёл/таймаут, завершение доворота
(smooth и мгновенного) — всё под `xru1.Cover.Debug`.

### Прогон 5 — подшаг заработал; единый источник правды для укрытия

Пользователь подтвердил: юниты прижимаются. Следующий рассинхрон: юнит на
рампе БЕЗ позы и иконки получал бонус укрытия от выстрелов — физика выстрела
(`GetCoverAgainst`) решала «что такое укрытие» заново и засчитывала любую
геометрию в 120 см (склон рампы, перепад пола).

Сделан ЕДИНЫЙ ИСТОЧНИК: стороны из `EvaluateSurroundings` — единственная
правда о стенах юнита (из неё уже растут поза, иконка, GE):

1. Плоскости всех сторон кэшируются в `CoverSidePlanes` при evaluate.
2. `GetCoverAgainst`: при `BestCoverAround == None` — сразу None; иначе бонус
   даёт только блокер, ЛЕЖАЩИЙ НА ПЛОСКОСТИ одной из своих стен (допуск
   `CoverPlaneTolerance` = 16 см, общий с удержанием active-стены). Физика
   осталась только вопросом ФЛАНГА.
3. `EvaluateCoverAtLocation` (план AI, превью хода): собирает стороны в
   проверяемой точке и гейтит так же — «план = факт» сохранён.
4. Следствие по правилам XCOM: чужая геометрия между стрелком и целью больше
   НЕ даёт цели бонус защиты — защищает только укрытие, у которого стоишь.

Потребители проверены: ComputeHitChance, HUD-щит (GetCoverShieldAgainst),
фланк-проверки, AI-план, превью — все идут через эти две функции.

### Прогон 6 — финальный аудит: вечный цикл выстрела AI

Лог: Marauder бесконечно повторяет выстрел по снайперу — «Begin chance=30.8 →
Reject invalid frozen solution → refund AP → повтор» (instances 10–24+, до
закрытия PIE).

**Причина — асимметрия ТОЧЕК ЦЕЛИ** (XCOM: боец в укрытии «занимает» и
соседний peek-тайл, симметрично для «видеть» и «быть увиденным»):

| Проверка | Точки цели (было) |
|---|---|
| Решение «видно ли» (HasLineOfSightFromLocation) | пики цели + корпус ✓ |
| Стойка/огневая точка (GetFiringStance) | ТОЛЬКО глаза + корпус ✗ |
| Огневые позиции для фланга (GetViableFiringPositions) | ТОЛЬКО глаза + корпус ✗ |
| Commit-валидация (HasLineOfSightFromFrozenOrigin) | пики цели + корпус ✓ |

Оба в полном укрытии: решение видит цель по паре пик×пик; стойка не находит НИ
ОДНОЙ позиции (глаза цели скрыты) и МОЛЧА падает в Open с центральным глазом;
commit честно отклоняет слепую точку; AP возвращается; детерминированный AI
повторяет. Побочно: GetViableFiringPositions пуст → GetCoverAgainst падал в
фолбэк «pos=1 от центра» — фланг тоже считался от слепой точки.

Починено:
1. `GetTargetExposedPoints` — ЕДИНСТВЕННЫЙ источник набора точек цели (центр +
   пики + корпус); переведены все четыре проверки.
2. GA_Attack::ActivateAbility валидирует замороженное решение ДО оплаты и ДО
   монтажа (тем же предикатом, что commit) — слепое решение отклоняется без
   анимации и без списания AP.
3. Предохранитель AI: цель с отклонённой активацией атаки блокируется до конца
   хода (`FailedAttackTargetsThisTurn`), утилити уходит на fallback-решения.
