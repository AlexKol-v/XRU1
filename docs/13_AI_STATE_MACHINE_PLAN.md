# ADR-1 — Архитектура принятия решений AI

> **Формат.** Architecture Decision Record: контекст → рассмотренные варианты →
> решение → следствия. Записан отдельно, потому что это самое дорогое решение
> блока: переделывать его позже будет стоить всей работы по AI.
> **Дата:** 2026-07-24. **Статус:** принято.

## ADR-1.1 — Контекст и требование

Требование сформулировано заказчиком дословно: *«наиболее современные и
взрослые правильные архитектурные решения»*, масштабируемость проверять на
конкретных будущих механиках — **перезарядка** и **бросок гранаты**, — и
отдельно: анимации добавляются позже, но обязаны **встроиться без переделки**.

Отдельно зафиксировано возражение: *«стейт-машина сейчас более гибкий и взрослый
инструмент»*. Возражение справедливое — и ниже разобрано по существу, а не
отмахиванием.

## ADR-1.2 — Разбор возражения про стейт-машины

Возражение верно **наполовину**, и важно понять, для какой именно половины.

**Где оно право.** Под «стейт-машиной» в UE5 сегодня обычно понимают не
`enum + switch`, а **UE StateTree** — иерархическую машину состояний, которая
соединила States/Transitions из FSM с Selector-узлами из Behavior Tree. Это
действительно современный и зрелый инструмент: production-ready начиная с
UE 5.5/5.6, собственный отладчик, и Epic рекомендует его как **default для
новых проектов** вместо Behavior Tree. Наш движок — 5.7, инструмент доступен.
Так что «стейт-машина взрослее BT» в 2026-м — правда, и старая редакция
[12_AI_REFERENCE §0](12_AI_REFERENCE.md#0-главный-вывод-у-решения-три-слоя-и-стейт-машина--только-один-из-них),
которая читалась как «FSM — вчерашний день», была сформулирована плохо и уже
исправлена.

**Где оно не право.** И FSM, и StateTree, и Behavior Tree отвечают на вопрос
**«в каком я состоянии / какую ветку выполняю»**. А решение хода в пошаговой
тактике — это вопрос **«какой из N доступных мне вариантов сейчас лучший»**.
Это сравнение, а не переход. Ни одна из трёх машин сравнения не делает: они
выбирают **первую подходящую** ветку по приоритету, а не **лучшую** по оценке.

Практическое следствие ровно то, что заказчик просил проверить:

| Механика | Стоимость в машине состояний | Стоимость в утилити |
|---|---|---|
| Добавить гранату | новое состояние + переходы **из каждого и в каждое** существующее (6 действий → 30 переходов, 9 → 72) | **один новый оценщик**, ноль правок |
| Добавить перезарядку | то же + условие «мало патронов» протаскивается во все ветки | один оценщик + одно слагаемое |
| Врагу другой характер | вторая копия дерева | другой **набор весов** (данные) |

Именно поэтому XCOM, будучи на Behavior Tree, **всё равно** держит под ним
утилити-скоринг: дерево выбирает «настроение» (профиль весов), а числа считает
скоринг. Тот же вывод независимо приходят современные разработчики пошаговых
тактик: BT/StateTree — для макро-стратегии, утилити — для конкретного действия.

## ADR-1.3 — Решение

**Слоёная архитектура; каждому слою — свой инструмент:**

| Слой | Инструмент | Обоснование |
|---|---|---|
| **Знание / тревога** (4 состояния) | **FSM** (`EUnitAlertState`) | состояний мало и они не комбинируются — FSM здесь уместна и останется |
| **Выбор действия** | **Утилити: набор подключаемых оценщиков** `UAIActionEvaluator` | сравнение N вариантов; линейное расширение |
| **Выбор цели / позиции** | **Аддитивный скоринг** (уже есть в `FindCoverPoint`) | то же |
| **Визуальное состояние** | **FSM** (`EUnitStance` в Anim Graph) | классический и единственно верный тут инструмент |
| **Фаза хода, режим ввода** | **FSM** (`ETurnPhase`, `EPlayerTargetingMode`) | уже реализовано, менять нечего |

Ключевой элемент — оценщик как **отдельный `UObject`-класс**, а не ветка кода:

```cpp
/**
 * Один вариант действия AI. Оценивает сам себя и сам себя исполняет.
 * Добавить новое поведение = добавить наследника и положить его в набор
 * (Data Asset). Существующие оценщики при этом НЕ ПРАВЯТСЯ — это и есть
 * критерий масштабируемости, ради которого выбрана утилити-архитектура.
 */
UCLASS(Abstract, EditInlineNew, DefaultToInstanced, BlueprintType, Blueprintable)
class XRU1_API UAIActionEvaluator : public UObject
{
    GENERATED_BODY()
public:
    /** Множитель итогового скора — «характер» юнита. Тюнится дизайнером. */
    UPROPERTY(EditAnywhere, Category = "AI", meta = (ClampMin = "0")) float Weight = 1.f;

    /** Дешёвый отсев до дорогой оценки (нет AP / нет способности / нет цели). */
    UFUNCTION(BlueprintNativeEvent, Category = "AI")
    bool IsApplicable(const FAIDecisionContext& Context) const;

    /**
     * Оценка варианта. Отрицательное значение = «никогда, если есть выбор»
     * (приём XCOM: -1000 вместо ветки-исключения).
     * ⚠️ Должна быть ЧИСТОЙ: ничего не менять в мире, чтобы порядок вызовов
     * оценщиков не влиял на результат.
     */
    UFUNCTION(BlueprintNativeEvent, Category = "AI")
    float ScoreAction(const FAIDecisionContext& Context, FAIDecision& OutDecision) const;
};
```

Набор оценщиков живёт в `UAITuningDataAsset` (фаза A6) — тем же приёмом, что
уже отработан на `UCoverTuningDataAsset`: глобальный ассет на GameInstance +
пер-юнитный override. Значит **новое поведение можно добавить, не трогая
контроллер**, а «характер» врага — вообще без кода.

`FAIDecisionContext` — снимок мира на одну активацию (юнит, AP, видимые враги,
союзники, тюнинг, номер хода). Он считается **один раз** и передаётся всем
оценщикам: без этого каждый заново собирал бы списки и перебор стал бы
квадратичным.

## ADR-1.4 — Доказательство масштабируемости

Проверка решения на механиках, названных заказчиком, и на анимациях.

**1. Бросок гранаты.**

| Что нужно | Куда ложится | Правки существующего кода |
|---|---|---|
| Способность | `UGA_Grenade : UTacticalAbility` (`ActionPointCost`, `bConsumesAllRemainingAP`, `MaxUsesPerMission` — всё уже в базе) | нет |
| Выбор AI | `UAIEval_ThrowGrenade` (скор = число целей в радиусе × урон − риск задеть своих) | нет |
| Анимация | новый `EUnitAction::ThrowGrenade` + монтаж | нет |
| ⚠️ **Чего не хватает** | **таргетинга по ТОЧКЕ**: `UTacticalAbility` умеет только `bRequiresTargetActor` (цель-актор). Граната летит в **клетку**, а не в бойца | **1 правка**: добавить `bRequiresTargetLocation` рядом с существующим флагом |

Вывод: одна честная правка в базовом классе способностей — и она **не про AI**,
а про таргетинг, то есть про игрока в равной степени. Это не изъян
архитектуры AI, но его нужно было найти заранее, что и сделано.

**2. Перезарядка.**

| Что нужно | Куда ложится | Правки существующего кода |
|---|---|---|
| Ресурс патронов | **новый `UAmmoComponent`** — ровно по образцу `UActionPointsComponent` (тот же паттерн «ресурс = компонент», уже проверен) | нет |
| Способность | `UGA_Reload : UTacticalAbility` | нет |
| Запрет выстрела без патронов | `UGA_Attack::GetTargetStatus` — новое значение `EAttackTargetStatus::NoAmmo` | **1 правка**, и она сразу даёт HUD правильную причину серой кнопки |
| Выбор AI | `UAIEval_Reload` (скор растёт при пустом магазине и отсутствии цели) | нет |
| Анимация | `EUnitAction::Reload` + монтаж | нет |

Вывод: одна правка в enum статуса цели, всё остальное — новые сущности.

**3. Анимации (главное требование «чтобы легко встроились позже»).**

Архитектура готова к анимациям, если выполнено три условия — и все три уже
заложены в фазах S1/S2:

- **единственная точка чтения** (`FUnitVisualState`) — ABP не опрашивает шесть
  систем, а читает одну структуру раз в кадр;
- **поза и действие разделены** — поза в State Machine, действие в Montage;
  добавление любого нового действия **не трогает** граф поз;
- **зеркало ничего не решает** — если анимации отключить, геймплей не заметит.

Проверка: добавление гранаты требует **одного** нового значения `EUnitAction` и
**одного** монтажа. Ни одна поза, ни один переход не правится. Это и есть
критерий «легко встроится».

**4. Новый архетип врага.** Другой набор весов и другой набор оценщиков в
`UAITuningDataAsset` — **ноль строк C++**.

## ADR-1.5 — Почему НЕ берём UE StateTree сейчас

Решение осознанное, с явным условием пересмотра — иначе через полгода никто не
вспомнит, почему.

**За:** Epic-native, визуальный отладчик, designer-editable, рекомендованный
default для новых проектов 2026.

**Против — по нашей конкретной ситуации:**

1. Слой, где StateTree был бы уместен (знание/тревога), содержит **4 состояния**.
   Заводить ради него модуль, схему, задачи-`USTRUCT`ы и ассет — инфраструктура
   дороже задачи в разы.
2. Основная сложность нашего AI — **в скоринге**, а не в топологии состояний.
   StateTree скоринг не делает; он всё равно вызывал бы утилити-слой, который
   мы и так пишем. То есть выигрыша по существу нет.
3. Пошаговая активация «одно решение — конец» плохо ложится на tick-ориентацию
   StateTree; пришлось бы гонять дерево вручную и гасить его же жизненный цикл.
4. Курсовой проект с фиксированным сроком: миграционный риск не окупается.

**Условие пересмотра (записать и проверять):** если появится **три и более**
архетипа врага с *принципиально разной логикой режимов* (не разными числами!),
слой знания/режима переносится на StateTree. Утилити-слой при этом **не
меняется вообще** — он подключается к StateTree ровно так же, как к FSM. Именно
ради этого он с самого начала оформлен отдельными `UObject`-оценщиками, а не
ветками внутри `StepCombat`.

**Переезд не «в теорию».** Донорский проект `cst-3d-gubkin-2026-04` уже
использует StateTree ([09_GAMEPLAY_STATUS §B.2](09_GAMEPLAY_STATUS.md)) — то
есть рабочий референс лежит рядом и читается в любой момент. Это дополнительный
аргумент **за** отложенное решение, а не против: путь разведан, платить за него
заранее не нужно.

## ADR-1.6 — Следствия

**Положительные:** линейное расширение; «характер» врага правится дизайнером
без кода; каждое решение объяснимо числом (лог «почему»); слои тестируются
раздельно; путь на StateTree открыт и дёшев.

**Отрицательные, принимаем сознательно:**

1. **Скоринг сложнее отлаживать, чем дерево** — «почему он это выбрал» не видно
   глазами. Лечится обязательным логом всех кандидатов с их скорами (фаза A9);
   **без этого лога утилити-архитектуру брать нельзя**.
2. **Веса требуют настройки.** Значения из XCOM — стартовая точка, не истина;
   заложить время на подбор.
3. **Больше классов** (оценщики). Компенсируется тем, что каждый мал и
   независим.

| Компоненты | `UActionPointsComponent`, `UCoverDetectionComponent`, `UNavigationInvokerComponent`, `UDecalComponent` (кольцо выбора) | ✅ полный набор |

| Способности | `AttackAbilityClass`, `OverwatchAbilityClass`, `HunkerAbilityClass`, `ClassAbilityClass`, `ClassAbilities[]` | ✅ хорошо: слоты, а не хардкод |
| Роль | `EUnitRole UnitRole` + восстановление в `BeginPlay` по классу | ✅ |
| Состояние | `bIsDead`, `bIsDowned`, `bIsEvacuated` + `OnUnitStateChanged` (делегат без параметров) | ⚠️ см. §I.3 |
| AI-данные | `PatrolPoints[]` | ⚠️ на юните, хотя это данные контроллера |
| Подсветка | `SetSelectionHighlight`, `SetHoverHighlight` (custom depth stencil) | ✅ |
| BP-хуки | `OnDied`, `OnDownedChanged`, `OnEvacuated` | ⚠️ только «выбывание» |

**Вывод по базе:** боевая часть архитектуры зрелая — единые слоты
способностей, статы под тюнинг из BP, GAS-атрибуты как единственный источник
HP. Проблема **не в боёвке, а в представлении состояния** (§I.3).

## I.2 Наследники: сейчас в них нет ничего, кроме дефолтов

[UnitClasses.cpp](../Source/XRU1/Tactics/UnitClasses.cpp) — 55 строк на четыре
класса. Каждый конструктор задаёт `UnitRole`, `UnitDisplayName`, статы и
`ClassAbilityClass`. **Ни одного переопределённого метода.**

| Класс | HP | Aim | Урон | Дальность | Классовая способность |
|---|---|---|---|---|---|
| `AUnit_Assault` «Клин» | 100 | 75 | 25 | 3000 | `UGA_RunAndGun` |
| `AUnit_Sniper` «Оса» | 80 | 85 | 40 | 5000 | — (пассивка Squadsight) |
| `AUnit_Healer` «Шприц» | 90 | 70 | 25 | 3000 | `UGA_Heal` |
| `AUnit_Tank` «Молот» | 150 | 70 | 25 | 3000 | `UGA_Taunt` |
| `BP_Unit_Marauder` (враг) | BP-наследник `AUnitBase` напрямую, без C++-класса | | | | |

**Это правильно и менять не надо.** «Тонкий наследник = набор чисел» —
здоровый паттерн: различия классов выражены данными, а не кодом, и дизайнер
правит их в BP. Ловушка была бы в обратном — начать писать в наследниках
`virtual` методы поведения.

**Единственный настоящий пробел наследников:** отсутствуют параметры, которые
AI-скоринг требует **на класс**, а не на юнита, — прежде всего **идеальная
дистанция боя** (§III, фаза A4). Снайпер и штурмовик обязаны хотеть разной
дистанции; сейчас у AI одна формула «ближе к цели» для всех.

## I.3 Где сейчас живёт состояние юнита — карта разброса ⭐

Это ключевая находка аудита. Состояние размазано по **шести** местам, и ни
одно из них не является полным:

| Что | Где живёт | Кто узнаёт об изменении |
|---|---|---|
| Жив / ранен / эвакуирован | `bIsDead`/`bIsDowned`/`bIsEvacuated` на `AUnitBase` | `OnUnitStateChanged` (**без параметров**) + BP-хуки `OnDied`/`OnDownedChanged` |
| Укрытие вокруг | `BestCoverAround` на `UCoverDetectionComponent` | `OnCoverStateChanged(ECoverType)` |
| **Направление укрытия** | **нигде — теряется внутри `EvaluateSurroundings`** | **никто** ⛔ |
| Теги стойки/статуса | GAS: `Cover.Half`, `Cover.Full`, `State.HunkeredDown`, `State.Taunting`, `State.Downed` | подписка на ASC |
| В движении | `AUnitAIController::IsMoving()` | опрос, делегата нет |
| Стойка выстрела | `EFiringStance` — **вычисляется по требованию** в `GetFiringStance` | никто не хранит |
| Тревога AI | `EUnitAlertState` на контроллере | никто |

Следствия, которые видно уже сейчас:

1. **`OnUnitStateChanged` — не «состояние», а «дёрнись, HUD».** Делегат без
   параметров: подписчик обязан сам опросить всё, что ему интересно. Для HUD
   это сошло, для анимации не годится — ABP не должен на каждый чих опрашивать
   шесть источников.
2. **Направление укрытия нигде не сохраняется.** `EvaluateSurroundings`
   перебирает направления, берёт лучший **тип** и выбрасывает направление.
   **Без него Ф10 физически не сделать**: чтобы юнит прижался к стене, ABP
   должен знать, где стена. Это не «доработка на будущее», а недостающее
   данное.
3. **Стойка выстрела не хранится.** `GetFiringStance` — чистая функция; в
   момент выстрела её результат никуда не кладётся, и анимации нечего читать.

## I.4 Диагноз: четыре архитектурные дыры

| № | Дыра | Что ломает | Где чиним |
|---|---|---|---|
| **D1** | Нет единого представления состояния юнита | анимации (Ф10), превью (Ф11), отладка AI | Часть II |
| **D2** | `EvaluateSurroundings` теряет направление укрытия | прижатие к стене, step-out, превью peek | Часть II, фаза S1 |
| **D3** | AI выбирает цель «ближайший», позицию — против **одной** угрозы | вся тактика врага | Часть III, фазы A3/A5 |
| **D4** | AI не пользуется Overwatch/Hunker, хотя они ему выданы | враг выглядит примитивным | Часть III, фаза A7 |
| **D5** ⭐ | **Овервотч срабатывает на ПОЯВЛЕНИЕ врага, а не на его движение** | наблюдение ботов не работает **вообще**: бойцы игрока обычно уже видны в момент постановки | Часть III, фаза **W1** |
| **D6** | Способности умеют целиться только в **актора**; таргетинга по точке нет | блокирует гранаты (ADR-1.4) | фаза W3 |
| **D7** | Нет ресурса «патроны» | блокирует перезарядку (ADR-1.4) | фаза W4, опционально |

**Разбор D5 (главная находка второго цикла аудита).**
[GA_Overwatch.cpp:89](../Source/XRU1/Tactics/GA_Overwatch.cpp:89)
подписывается на `OnTargetPerceptionUpdated` и стреляет по стимулу «увидел».
Ограничение честно записано в комментарии заголовка: *«реакция срабатывает на
ВХОД врага в зону видимости; перемещение врага целиком внутри зоны повторного
стимула не даёт»*.

Для наблюдения **игрока** это почти не мешает — враги приходят издалека и
пересекают границу восприятия. Для наблюдения **ботов** это отключает механику
полностью: враг встаёт в овервотч, **уже видя** бойцов игрока; те двигаются
внутри зоны — нового стимула нет — реакции нет никогда.

В XCOM 2 условие другое: наблюдающий должен **увидеть движение** — видимость
двух клеток подряд на пути врага
([12_AI_REFERENCE §VII.2.2](12_AI_REFERENCE.md#vii22-что-именно-вызывает-реакционный-выстрел)).

# Часть II — Единая точка состояния юнита (для анимаций)

## II.1 Прямой ответ на вопрос

> «Есть ли у нас единая точка для базового юнита, откуда можно брать состояние
> для смены анимаций?»

**Нет.** Есть `AUnitBase::OnUnitStateChanged` — но это сигнал «что-то
изменилось» без данных, и он покрывает только жизненный цикл (смерть/ранение/
эвакуация), а не боевую стойку. Ни укрытие, ни прицеливание, ни выстрел, ни
направление стены через него не проходят. Анимационно значимое состояние
собирается из шести разных мест (§I.3).

**Архитектура при этом не «неправильная» — она недостроенная.** Все нужные
данные в системе есть и считаются корректно, единым источником правды; не
хватает **слоя представления**: одной структуры, куда системы кладут результат,
и одного делегата, на который подписывается ABP.

Что важно: этот слой обязан быть **только зеркалом**. Он ничего не решает и ни
на что не влияет — иначе мы заведём второй источник правды и нарушим инвариант
«план == факт» из 11-го плана.

## II.2 Что реально должна знать анимация

Разбор по сценариям, названным в вопросе:

| Сценарий | Что нужно ABP | Есть? |
|---|---|---|
| Half cover → присесть | тип укрытия | ✅ `BestCoverAround` |
| Full cover → вжаться в стену | тип укрытия + **сторона стены** | ⛔ направления нет (D2) |
| Прицеливание → стойка «в прицел» | «сейчас целюсь» + куда | ⛔ живёт только в контроллере игрока |
| Выстрел | событие + попал/промазал | ✅ `OnShotFired(Target, bHit)` в `GA_Attack` |
| Выстрел поверх низкого укрытия | `EFiringStance::OverCover` | 🟡 считается, не хранится |
| Выбежать из-за высокого и выстрелить | `EFiringStance::StepOut` + **точка выхода** | 🟡 `GetFiringStance` отдаёт и то, и другое, но никто не сохраняет |
| Овервотч | «стою на реакции» | ✅ тег GAS |
| Глухая оборона | «вжался максимально» | ✅ тег `State.HunkeredDown` |
| Бег / стоп | скорость + `IsMoving()` | ✅ (локомоушен уже работает) |
| Ранение / смерть | флаги + хуки | ✅ |

Итог: **не хватает трёх данных** — направление укрытия, факт прицеливания,
сохранённая стойка выстрела. Остальное уже есть, просто разбросано.

## II.3 Ключевое разделение: ПОЗА ≠ ДЕЙСТВИЕ

Главное проектное решение, которое стоит принять до кода. Смешение этих двух
вещей в один enum — самая частая ошибка в анимации пошаговых игр.

| | **Поза** (`EUnitStance`) | **Действие** (`EUnitAction`) |
|---|---|---|
| Природа | длительное состояние | одноразовое событие |
| Меняется | при перемещении, смене укрытия, ранении | по команде игрока/AI |
| В ABP | **State Machine** в Anim Graph | **Montage** в слоте поверх позы |
| Длительность | пока не сменится | пока играет монтаж |
| Примеры | стоя / присев за низким / вжался в высокое / лежит раненым / мёртв | выстрел, выстрел поверх укрытия, выбежать-выстрелить, встать в овервотч, глухая оборона, лечение, провокация |

Почему это принципиально: «выстрел» — **не поза**. Юнит стреляет **из** позы и
**возвращается** в неё. Если сделать `Firing` состоянием стейт-машины, придётся
руками писать переходы «из чего пришёл — туда и вернись» для каждой пары, и
их число растёт квадратично. С монтажом поверх позы возвратов не нужно вовсе.

Отсюда вытекает и правило для Ф10: `StepOut` — это **монтаж со смещением
корня**, а не смена позы и не телепорт. Геймплейная позиция, укрытие и диск
занятости остаются на настоящей клетке (инвариант «peek — не телепорт»,
[11_COVER_AND_ENEMY_PLAN §V.2 п.5](11_COVER_AND_ENEMY_PLAN.md#v2-инварианты--не-ломать)).

## II.4 Предлагаемая архитектура

Новый файл `Source/XRU1/Tactics/UnitVisualState.h` (рядом с `CoverTypes.h` —
там же живут `ECoverType`/`EFiringStance`, и его включают и UI, и геймплей):

```cpp
/** ПОЗА юнита — длительное состояние для State Machine в Anim Graph. */
UENUM(BlueprintType)
enum class EUnitStance : uint8
{
    Stand      UMETA(DisplayName = "Stand"),        // открыт / бежит
    CoverLow   UMETA(DisplayName = "Cover Low"),    // присел за низким
    CoverHigh  UMETA(DisplayName = "Cover High"),   // вжался в высокое
    Hunkered   UMETA(DisplayName = "Hunkered"),     // глухая оборона
    Overwatch  UMETA(DisplayName = "Overwatch"),    // на реакции
    Downed     UMETA(DisplayName = "Downed"),
    Dead       UMETA(DisplayName = "Dead")
};

/** ДЕЙСТВИЕ — одноразовое, играется монтажом поверх позы. */
UENUM(BlueprintType)
enum class EUnitAction : uint8
{
    None, Fire, FireOverCover, FireStepOut, EnterOverwatch, EnterHunker,
    Heal, Taunt, Hit, Death
};

/**
 * ЗЕРКАЛО состояния юнита для анимации/UI/превью. Ничего не решает и ни на что
 * не влияет: системы (укрытие, GAS, AI, контроллер) меняют своё состояние
 * ПЕРВЫМИ и только потом обновляют зеркало. Единственный потребитель, который
 * имеет право читать это вместо первоисточника, — представление.
 */
USTRUCT(BlueprintType)
struct FUnitVisualState
{
    GENERATED_BODY()

    /** Поза. */
    UPROPERTY(BlueprintReadOnly) EUnitStance Stance = EUnitStance::Stand;

    /** Тип лучшего укрытия вокруг (дублирует BestCoverAround — для одного чтения). */
    UPROPERTY(BlueprintReadOnly) ECoverType Cover = ECoverType::None;

    /**
     * Направление НА СТЕНУ укрытия (нормаль в мире, XY). Zero — укрытия нет.
     * ⚠️ Данное, которого сегодня не существует нигде (дыра D2). Без него
     * невозможно развернуть бойца спиной к стене.
     */
    UPROPERTY(BlueprintReadOnly) FVector CoverDirection = FVector::ZeroVector;

    /** Юнит целится (взял цель на прицел, выстрел ещё не разыгран). */
    UPROPERTY(BlueprintReadOnly) bool bAiming = false;

    /** Куда целится/стреляет (мировая точка). */
    UPROPERTY(BlueprintReadOnly) FVector AimLocation = FVector::ZeroVector;

    /** Как будет стрелять из текущей позиции (Open / OverCover / StepOut). */
    UPROPERTY(BlueprintReadOnly) EFiringStance FiringStance = EFiringStance::Open;

    /**
     * Куда физически смещается корпус при StepOut (мировая точка глаз из
     * GetFiringStance). ⚠️ ВИЗУАЛЬНОЕ смещение с возвратом — не позиция юнита.
     */
    UPROPERTY(BlueprintReadOnly) FVector StepOutLocation = FVector::ZeroVector;

    /** Юнит перемещается (для локомоушена; источник — AIController::IsMoving). */
    UPROPERTY(BlueprintReadOnly) bool bMoving = false;
};
```

На `AUnitBase` добавляется:

```cpp
DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FOnUnitVisualStateChanged, const FUnitVisualState&, NewState);
DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FOnUnitAction, EUnitAction, Action);

/** ЕДИНАЯ точка чтения состояния для анимаций/UI/превью. */
UFUNCTION(BlueprintPure, Category = "Tactics|Visual")
const FUnitVisualState& GetVisualState() const { return VisualState; }

/** Пересобрать зеркало из первоисточников; шлёт делегат, только если изменилось. */
UFUNCTION(BlueprintCallable, Category = "Tactics|Visual")
void RefreshVisualState();

/** Разовое действие (монтаж). Не меняет позу. */
UFUNCTION(BlueprintCallable, Category = "Tactics|Visual")
void NotifyUnitAction(EUnitAction Action);

UPROPERTY(BlueprintAssignable, Category = "Tactics|Visual") FOnUnitVisualStateChanged OnVisualStateChanged;
UPROPERTY(BlueprintAssignable, Category = "Tactics|Visual") FOnUnitAction              OnUnitAction;
```

## II.5 Кто что заполняет (источники)

Ни одно поле зеркала не «изобретается» — у каждого есть первоисточник:

| Поле | Первоисточник | Кто дёргает `RefreshVisualState` |
|---|---|---|
| `Cover`, `CoverDirection` | `UCoverDetectionComponent` | `EvaluateSurroundings` после пересчёта |
| `Stance` | производная: `bIsDead`/`bIsDowned` → теги GAS (`HunkeredDown`, `Overwatch`) → `Cover` | тот же вызов |
| `bAiming`, `AimLocation` | `ATacticalPlayerController` (`EPlayerTargetingMode`) / AI при выборе цели | смена режима прицеливания |
| `FiringStance`, `StepOutLocation` | `UTacticsCombatStatics::GetFiringStance` | перед выстрелом в `GA_Attack` |
| `bMoving` | `UTacticsCombatStatics::IsUnitInTransit` | старт/финиш движения (`OnMoveCompleted`) |

**Приоритет позы фиксированный и сверху вниз:**
`Dead` → `Downed` → `Hunkered` → `Overwatch` → `CoverHigh` → `CoverLow` → `Stand`.
Один порядок в одном месте — иначе «вжался, но при этом в овервотче» станет
неопределённым.

## II.6 Как это читает Anim Blueprint

Сейчас все пять BP-юнитов используют шаблонный **`ABP_Unarmed`** из
`Content/Characters/Mannequins/Anims/Unarmed/`, а собственная папка
`Content/XRU1Game/Units/Anims/` **пуста**. То есть анимационный слой ещё не
начат вовсе — и это удачно: делать его поверх готового зеркала проще, чем
переделывать.

Схема без сюрпризов:

1. `ABP_Unit` (наследник или копия `ABP_Unarmed`) в `Event Blueprint Update
   Animation`: `TryGetPawnOwner` → `Cast to UnitBase` → `GetVisualState()` →
   разложить в переменные ABP (одно чтение на кадр, без опроса шести систем).
2. **Anim Graph:** State Machine по `Stance` (7 состояний), внутри `Stand` —
   существующий локомоушен по скорости.
3. **Слот монтажа** поверх результата State Machine; монтажи запускаются по
   `OnUnitAction`.
4. **Направление стены** — доворот в `CoverDirection` через Rotate Root Bone
   или aim offset, не поворотом актора (иначе разъедется с `FaceActorTowards`
   при выстреле).

## II.7 Что в базу, а что по классам

| Уровень | Что кладём |
|---|---|
| **`AUnitBase` (все)** | `FUnitVisualState` + делегаты; `EUnitStance`/`EUnitAction`; направление укрытия; идеальная дистанция боя (нужна AI-скорингу, §III A4); профиль весов AI по умолчанию |
| **C++-наследники классов** | только **числа** в конструкторе — как сейчас. Дополнительно: своя идеальная дистанция (снайпер — далеко, штурмовик — вплотную) и свой AI-профиль весов |
| **BP-наследники** | скелет, меш, `ABP_Unit`, набор монтажей на `EUnitAction`, VFX/звук |
| **Никогда** | `virtual` методы поведения в наследниках классов — различия выражаются данными |

Отдельно: **`PatrolPoints` стоит оставить на `AUnitBase`**, хотя логически это
данные AI. Причина прагматичная — точки расставляются на инстансе актора в
редакторе (`EditInstanceOnly`), а контроллер в редакторе не виден. Менять не
надо, но в комментарии стоит это зафиксировать.

## W1 — Овервотч срабатывает на ДВИЖЕНИЕ `[x]` СОБРАНО ⭐ (дыра D5)

>
> **Два триггера, второй — надмножество первого.** Старый
> (`OnTargetPerceptionUpdated`, «враг появился») оставлен нетронутым; добавлен
> периодический опрос движущихся врагов (`CheckMovingTargets`, таймер
> `ReactionCheckInterval = 0.1 с`). Реакция засчитывается, когда цель прошла
> `ReactionMinTravel = 50 см` от точки начала ТЕКУЩЕГО перемещения (наш аналог
> клетки XCOM). Факт движения — единый предикат `IsUnitInTransit`.
>
> **Оба триггера идут через ЕДИНЫЙ `TryReactTo`** (фаза хода, лимит реакций,
> `CanTargetActor`, «по этому перемещению уже стреляли»). Без общей точки
> появление врага и его же движение дали бы два выстрела за один шаг.
>
> **Одна реакция на одно НЕПРЕРЫВНОЕ перемещение:** цель помечается в
> `ReactedThisMove` и снова становится «свежей», только когда остановится.

Без этой фазы фаза A7 («AI умеет овервотч») бессмысленна: бот встанет в
наблюдение и никогда не выстрелит.

- Заменить триггер: вместо (только) `OnTargetPerceptionUpdated` — **проверка
  движущихся врагов**. Источник факта движения уже есть и он единый —
  `UTacticsCombatStatics::IsUnitInTransit` (спрашивает path following
  контроллера, а не velocity).
- Условие выстрела не меняется: тот же `UGA_Attack::CanTargetActor`
  (враждебность, живость, дальность, LOS/peek). Так наблюдение автоматически
  наследует всю геометрию Ф4/Ф5 — включая выстрел из-за края укрытия.
- **Дискретизация вместо «двух клеток подряд».** У XCOM тайлы, у нас навмеш.
  Аналог: реакция проверяется не каждый кадр, а раз в
  `ReactionCheckInterval` (≈0.1 с) **и** после того, как цель прошла
  `ReactionMinTravel` (≈50 см) с момента постановки. Смысл тот же —
  «шевельнулся заметно», а не «дрогнул на месте».
- **Перевыбор цели** (требование B5b): если реакций осталось больше нуля, а
  цель убита — следующий стимул обрабатывается как обычно; специального кода
  не нужно, но проверить, что `EndAbility` не вызывается раньше времени.
- ⚠️ **Не ломать существующее поведение игрока.** Старый путь (реакция на вход
  в зону) остаётся как **дополнительный** — новый триггер его надмножество.
  Регрессия «овервотч игрока перестал ловить выбегающих» недопустима.
- ⚠️ **Одна реакция на одно перемещение.** После выстрела способность
  завершается (`MaxReactionShots`), но пока она жива, нельзя стрелять по одному
  и тому же непрерывному движению дважды.
- **Приёмка:**
  1. враг ставит наблюдение, видя бойца; боец **двигается** в поле зрения →
     реакционный выстрел проходит (до правки — не проходил никогда);
  2. боец стоит на месте → реакции нет;
  3. регрессия: боец игрока в наблюдении по-прежнему стреляет по врагу,
     выбегающему из-за угла;
  4. один выстрел на одно перемещение, не очередь.

## S1 — Направление укрытия `[x]` СОБРАНО (дыра D2)

> **Статус (2026-07-24):** сделано раньше плана — понадобилось не анимации, а

>
> **Что было не так.** «Укрытие против стрелка» решалось ОДНИМ лучом «есть ли

> прикрывает **полуплоскость** со своей стороны; атака, не попавшая ни в одну
> защитную дугу, — фланг. Для этого нужна ОРИЕНТАЦИЯ стены, а не только тип.
>

> - `FCoverSide` (`CoverTypes.h`): направление на стену + тип + дистанция;
> - `GatherCoverSides` — лучи по кругу, стороны склеиваются **по нормали стены**
>   (`ImpactNormal`), поэтому плоская стена даёт ОДНУ сторону, а не три луча;
>   стены дальше `CoverSideDistanceSlack` от ближайшей отбрасываются («прячусь
>   за ближней, а не за всем в радиусе»);
> - ~~`BestCoverAgainstDirection` — дуга `CoverArcHalfAngle`~~ ⚠️ **отменено в
>   цикле 10**: угловая модель заменена на физику выстрела, обе сущности удалены
>   (см. §«Цикл 10»);
> - `GetCoverAgainst` и `EvaluateCoverAtLocation` переведены на эту математику
>   (план == факт), **стороны пересобираются трейсами на каждый вызов** — кэш
>   укрытия против врага по-прежнему запрещён (§V.2 п.4);
> - `CoverSides` + `BestCoverDirection` на компоненте — это и есть данное,
>   которого не хватало анимации (Ф10);
> - отладка: при `xru1.LOS.Debug 1` рисуется стрелка на стену и **границы
>   защитной дуги** — видно, откуда можно зайти во фланг.
>
> **Тюнинг, если фланг всё ещё редкий (актуально после цикла 10):** единственная
> ручка — `CoverTraceDistance` (120 → 80: «в укрытии» = вплотную к стене, как

## A4 — Идеальная дистанция боя `[x]` СОБРАНО

> **Статус (2026-07-24):** сделано вне очереди — оказалось **прямой причиной**
> жалобы «боты сближаются вплотную».
>
> **Диагноз по логам.** Дистанцию до A4 оценивал единственный член
> `OverextendPenaltyPerCm`, считавшийся от `0.75 × AttackRange`. `AttackRange` —
> щедрый технический cap (3000), значит порог ≈ 2250 см, и на нашей карте штраф
> не срабатывал **ни разу**. Дистанция фактически не влияла на выбор позиции:
> укрытие тянуло прятаться, линия огня — видеть цель, а «не подходи вплотную»
> не говорил никто.
>
> **Реализация:** `AUnitBase::IdealCombatRange` (по классам: штурмовик 450,
> танк 600, медик 1100, снайпер 2200, база/мародёр 900) + член скоринга по
> формуле XCOM `1 − |dist − ideal| / falloff`, вес `IdealRangeWeight = 30`
> (в XCOM `fDistanceWeight` 4–5 — один из самых больших, против
> `fCoverWeight` 1.7–2.0). `OverextendPenaltyPerCm` удалён как мёртвый.
>
> ⚠️ **Отклонение от собственного плана.** План предписывал брать идеал как
> максимум `AimByDistanceCurve`. Так делать нельзя: у встроенного профиля
> винтовки максимум точности — **в упор** (+10), то есть «идеалом» оказался бы
> нулевой зазор, и формула поощряла бы ровно то поведение, которое чиним.
> Дистанция боя — решение дизайнера, а не побочный эффект кривой оружия.

## A4 (исходная постановка)

- `AUnitBase`: `IdealCombatRange` (см), `EditAnywhere`. Дефолты по классам:

  правды о том, где юниту хорошо стрелять.
- Скоринг дистанции переводится с «чем ближе, тем лучше» на «чем ближе к

## A5 — Скоринг позиции: все угрозы, фланг, высота, кучность `[x]` СОБРАНО ⭐

> **Статус (2026-07-24):** реализовано и собрано. Закрывает остаток Ф9 и дыру D3,
> и это же фаза, которая чинит **«боты кровожадно бегут в атаку, не защищаясь»**.
>
> **Что изменилось в `FindCoverPoint`:**
> - укрытие точки считается **против всех видимых угроз** усреднением
>   (`CoverValueAgainstAll`), а не против одной;
> - открытость даёт **резко отрицательный** вклад `OpenCoverFactor = −4.0`
>   (XCOM `CALC_NO_COVER_FACTOR`). При `CoverDefenseWeight = 20` укрытая точка
>   даёт ≈ +22, открытая ≈ −80: разрыв в 100 очков заведомо перекрывает

>   бота искать укрытие** — «AI боится флангов» в XCOM работает так же;
> - `FullCoverFactor = 1.1` против `HalfCoverFactor = 1.0` — полное укрытие
>   ценнее половинчатого всего на 10% (из него труднее стрелять). ⚠️ Не
>   подгонять под соотношение защиты 40/20, это разные вещи;
> - `FlankPositionBonus` — за точку, из которой юнит сам кого-то фланкирует
>   (новая `IsTargetFlankedByLocation`: план и факт одной математикой);
> - `HeightPositionBonus` — за превышение над целью по порогу
>   `DA_CoverTuning.HeightAdvantageZ`;
> - `MinSpreadDistance` / `SpreadPenaltyMultiplier` — штраф за кучность,
>   множителем и **только к положительному** скору (к отрицательному он делал бы
>   плохую точку лучше).

> **Производительность.** Стороны укрытия собираются ОДИН раз на точку (дорого —
> трейсы), а против каждой угрозы проверяется только дуга (бесплатно).
>
> ⚠️ **Устарело после цикла 10.** Угловая модель убрана: теперь на каждую угрозу
> идёт свой трейс укрытия плюс проверка линии огня. Цена снова зависит от числа
> врагов, поэтому и введены `MaxScoredThreats` (4, как `MAX_EXPECTED_ENEMY_COUNT`
> в XCOM), проверка достижимости ПЕРЕД оценкой и отсечение по потолку скора.
>
> **Найденная попутно ошибка:** базовая линия считалась от `ActorLocation`
> (центр капсулы), а кандидаты — от точки пола навмеша. Укрытие трассировалось
> на 88 см выше, то есть текущая позиция и кандидаты судились разными
> правилами. Исправлено (`UnitFloor`).
>
> **Диагностика:** при `xru1.AI.LogCombat 1` печатается строка
> `позиция найдена/НЕ найдена: база X (укрытие Y по N угрозам), лучшая Z,
> порог W` — по ней настраиваются веса.

## A5 (исходная постановка)

Доработка `FindCoverPoint`. Закрывает остаток Ф9 и дыру D3.

1. **Укрытие против ВСЕХ видимых угроз, усреднением** — формула
   [12_AI_REFERENCE §IV.1](12_AI_REFERENCE.md#iv1-метрики-тайла):

   ```
   CoverValue = (N_open*OpenFactor + N_half*HalfFactor + N_full*FullFactor) / N_total
   ```

   с резко отрицательным `OpenFactor` (XCOM: −4.0 против +1.0/+1.1). Именно
   отрицательный коэффициент, а не спецправило, даёт «AI боится флангов».
   ⚠️ Заметить: в XCOM полное укрытие ценнее половинчатого **всего на 10%**
   (1.1 против 1.0) — из полного труднее стрелять. Копируем это соотношение,
   а не «40 против 20» из чисел защиты.
2. **Вес фланга:** точка, из которой юнит фланкирует хоть кого-то (`IsTargetFlankedBy`
   в обратную сторону), получает бонус. Профиль «обходчик» — вес 10 при
   укрытии 1 (XCOM `Flanking`).
3. **Вес высоты:** у нас уже есть `HeightAdvantageZ`/`HeightAdvantageAimBonus`
   в `DA_CoverTuning` — добавить нормированное превышение в скор.
4. **Штраф за кучность:** точка ближе `MinSpreadDistance` к союзнику домножает
   **положительный** скор на `SpreadMultiplier` (< 1). Только положительный —
   иначе штраф превратится в поощрение для отрицательных скоров.
5. **Оставить как есть:** `RelocateBias` (порог значимости) и `BaselineScore`
   (скоринг дельтой) — это уже правильные реализации `CURR_TILE_LINGER_PENALTY`
   и дельта-скоринга XCOM.
- **Приёмка:** враг не встаёт в точку, открытую хотя бы одному бойцу отряда,
  если есть альтернатива; два врага не лезут в одно укрытие; при равных
  укрытиях выбирает верхнее.

  ⏭ Второй случай из XCOM (юнит, упёршийся в лимит атакующих, тоже уходит в

  `CanActivateAbility`» — неверно как основание НЕ проверять его в оценщике.
  Способность проверяет `BestCoverAround` (тег Cover.*), а контекст AI знает
  `bExposed` (укрытие против конкретной угрозы). Оценщик проверяет ОБА.
- ✅ **`SafeToMove`** — сделано 2026-07-25. `FAICoverPointResult::ThreatsOverwatching`
  считается ВНУТРИ уже существующей проверки видимости (`EvaluatePoint`, шаг 2b)

  видит меня, а если на нём тег `State.Overwatch` — встретит реакционным
  выстрелом. Штраф `OverwatchExposurePenalty` (30) за КАЖДОГО наблюдателя.
  ⚠️ Осознанное упрощение: проверяется КОНЕЧНАЯ точка, а не весь маршрут
  (в XCOM — маршрут). Полная проверка пути стоила бы отдельного перебора LOS по
  каждому отрезку каждого из 48 кандидатов, а конечная точка — доминирующий
  член: именно на ней юнит стоит весь ход противника.
- **Приёмка:** враг, которому некуда стрелять, иногда встаёт в овервотч (не
  всегда); раненый враг в укрытии уходит в глухую оборону; враг не бежит в точку,
  простреливаемую двумя овервотчами, если есть альтернатива.

## A9 — Каркас: контекст, оценщики, лог `[x]` СОБРАНО

> **Статус (2026-07-24):** реализовано и собрано (`Result: Succeeded`).
> Новые файлы: [AIDecisionTypes.h](../Source/XRU1/Tactics/AIDecisionTypes.h)
> (`EAIActionKind`, `FAIDecision`, `FAIDecisionContext`),
> [AIActionEvaluator.h](../Source/XRU1/Tactics/AIActionEvaluator.h) (база),
> [AIActionEvaluators.h/.cpp](../Source/XRU1/Tactics/AIActionEvaluators.cpp)
> (5 оценщиков). В `AUnitAIController`: `ActionEvaluators` (Instanced-набор,
> собирается в конструкторе), `BuildDecisionContext`, `DecideAction`,
> `ExecuteDecision`; `FindCoverPoint` стал публичным (его зовут оценщики).
>
> ⚠️ **Поведение НЕ менялось и не должно было.** Базовые приоритеты
> (Retreat 100 > MoveToCover 80 > Shoot 60 > AdvanceToCover 40 >
> CloseDistance 20) вместе с отсечением по потолку воспроизводят прежний
> приоритетный список один в один — включая число дорогих вызовов
> `FindCoverPoint`. Любое изменение поведения после этой фазы — **баг**.
>
> **Отсечение по потолку (`GetMaxPossibleScore`).** Набор сортируется по
> верхней границе скора убыванием; как только текущий лучший результат её
> достиг, перебор обрывается. Без этого три «двигательных» оценщика утроили бы
> время хода врага (каждый зовёт `FindCoverPoint` = 48 точек × трейсы LOS) —
> ровно тот риск, что отмечен в Ф5. **Контракт:** `ScoreAction` никогда не
> возвращает больше `BasePriority`, иначе отсечение начнёт терять лучшие
> варианты.

Технический долг, который окупается сразу:

```cpp
/** Решение AI на одну активацию — что делать и с чем. Исполняется отдельно. */
USTRUCT()
struct FAIDecision
{
    GENERATED_BODY()
    UPROPERTY() EAIActionKind Kind = EAIActionKind::Skip; // Shoot/Move/Overwatch/Hunker/Skip
    UPROPERTY() TObjectPtr<AActor> Target = nullptr;
    UPROPERTY() FVector Destination = FVector::ZeroVector;
    UPROPERTY() FName   MoveProfile;   // какой профиль весов выбран
    UPROPERTY() float   Score = 0.f;
    UPROPERTY() FString Reason;        // человекочитаемо, под xru1.AI.LogCombat
};
```

`StepCombat` возвращает `FAIDecision`, отдельный `ExecuteDecision` его
исполняет. Это даёт: один лог на решение (видно **почему**), возможность
показать намерение врага в отладке, и естественную точку для Ф10 (анимация
знает, что сейчас будет).

- **Приёмка:** `xru1.AI.LogCombat 1` печатает одну строку на активацию:
  действие, цель, профиль, скор, причина.

# Часть VI — Инварианты

Дополняют [11_COVER_AND_ENEMY_PLAN §V.2](11_COVER_AND_ENEMY_PLAN.md#v2-инварианты--не-ломать),
не отменяют их.

1. **Состояний тревоги ровно четыре.** Новое поведение = новый **оценщик** или
   вес, **никогда** не новое состояние FSM
   ([12_AI_REFERENCE §0](12_AI_REFERENCE.md#0-главный-вывод-у-решения-три-слоя-и-стейт-машина--только-один-из-них),
   [ADR-1](#adr-1--архитектура-принятия-решений-ai)).
   - **Оценщики чистые.** `ScoreAction` ничего не меняет в мире: иначе результат
     зависит от порядка вызова оценщиков и решение невоспроизводимо.
   - **Контекст считается один раз на активацию** (`FAIDecisionContext`) и
     передаётся всем оценщикам — иначе перебор станет квадратичным.
   - **Лог кандидатов обязателен.** Утилити-решение необъяснимо без вывода всех
     вариантов со скорами; выкидывать этот лог из плана нельзя (ADR-1.6).
2. **Зеркало состояния ничего не решает.** `FUnitVisualState` — только чтение
   для представления. Любая геймплейная проверка обязана идти к первоисточнику
   (`CoverDetection`, ASC, `TacticsCombatStatics`), иначе появится второй
   источник правды.
3. **Поза и действие раздельны.** Поза — State Machine, действие — Montage.
   Выстрел никогда не становится позой.
4. **Peek — не телепорт** (перенос из 11-го плана). `StepOutLocation` —
   визуальное смещение с возвратом; укрытие, диск занятости и геймплейная
   позиция остаются на настоящей клетке.
5. **AI и игрок судят по одним функциям.** `CanTargetActor`, `HasLineOfSight*`,
   `GetMoveCostForDistance`, `ComputeAttackHitChance` — общие. Параллельных
   реализаций «для AI» не заводить.
6. **AI не читерит знанием.** Всё знание — через перцепцию и журнал наблюдений.
   Прямое чтение позиций отряда в обход этого запрещено.
7. **Ход не может зависнуть.** У списка правил всегда есть терминальный
   фолбэк (пропуск хода). Провал любого правила ведёт к следующему, последний —
   к завершению активации.
8. **Дефолты новых Data Asset равны текущим числам** — до назначения ассета
   поведение не меняется (приём, отработанный в Ф3).
9. **Новые параметры публичных `UFUNCTION` — только со значением по умолчанию.**
10. **Донор — read-only.**

## A5+ — «Осознанное укрытие» `[x]` СОБРАНО

> **Требование игрока:** в момент выбора точки юнит обязан знать, **от кого он
> там закрыт** и **кого оттуда простреливает**, а добежать — именно туда, куда
> решил.
>
> **Что было не так.** Оценка сводилась к среднему баллу укрытия по всем
> угрозам плюс ОДНА проверка линии огня — по «основной» цели. Точка, из которой
> простреливается сосед, но не главный враг, честно считалась бесполезной. А
> сколько врагов оттуда видно и от скольких из них точка закрыта — не знал никто,
> включая лог.
>
> **Как в XCOM.** `ai_tile_score` считает `fCoverValue` **по каждому врагу**
> (сколько флангуют / half / full) и отдельно `fEnemyVisibility` — сколько
> врагов видно с клетки (шаг `1/MAX_EXPECTED_ENEMY_COUNT`, по умолчанию ¼;
> −1, если не видно никого). То есть XCOM тоже знает поимённо.
>
> **Реализация:**
> - `FAICoverPointResult` — что именно даёт точка: `ThreatsCovered`,
>   `ThreatsExposed`, `ThreatsVisible`, `ThreatsFlanked`, `Score`;
> - `EvaluatePoint` считает это **по каждой угрозе отдельно**: закрыт ли,
>   видно ли (тем же предикатом, что решает выстрел, из тех же огневых позиций
>   peek), фланкирую ли;
> - новый член `EnemyVisibilityWeight` — «сколько врагов видно», −1×вес, если
>   не видно никого: **укрытие, из которого нельзя ответить, — это не позиция,
>   а угол**;
> - `bCanShoot` теперь = «вижу ЛЮБУЮ угрозу», а не только основную цель;
> - `MaxScoredThreats` (аналог `MAX_EXPECTED_ENEMY_COUNT` = 4) ограничивает
>   перебор ближайшими: проверка LOS из каждой точки по каждой угрозе — самая
>   дорогая часть;
> - причина решения в логе теперь содержит расшифровку:
>   `закрыт от 2/3, вижу 1, фланкую 0`, и рядом — то же для текущей позиции.
>
> **«Бежит именно туда, куда выбрал».** Приказ идёт ровно в выбранную точку (она
> уже проверена на достижимость и занятость внутри `FindCoverPoint`), а по
> прибытии сверяется факт: при расхождении больше `ManeuverArrivalTolerance`
> в лог идёт `Warning` с обеими координатами и фактическим укрытием на месте.
> Это не косметика: расхождение означает, что укрытие оценивалось в одной
> точке, а юнит стоит в другой, где оно может не работать.

**Разделение слоёв, ради которого всё делалось.** Логика («останавливает ли
стена этот выстрел») — луч от цели к огневой позиции стрелка. Визуал («к чему я
прижат») — `CoverSides` / `BestCoverDirection`. Второй слой больше **не влияет**
на фланг, поэтому анимацию можно делать (или не делать) как угодно.
